# Maestro Agent Skill Bundle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn four generic primitives into competence. An agent that
installs this bundle arrives at a fresh Maestro game already knowing that
it must declare a vocabulary before it can write anything, that a
reference to another entity is a relation and never a field, that keys
are the API, that writes are versioned and batches are bounded, and that
composing a view is a validate loop. It learns none of this by reading a
second copy of the tool descriptions.

**Architecture:** One new package, `internal/skill`, holding the bundle
as `//go:embed`ed files, a stable content hash over them, a zip served
over a signed, short-lived URL, and one MCP tool — `skill.install` —
that returns a descriptor and never the bytes. Everything else in this
sub-project is a **guard**: the bundle is the only artefact in this
repository written in prose for a machine to act on, and prose is the one
thing the previous forty tasks proved cannot be trusted without a test
reading it back.

**Tech Stack:** Go 1.25.7, `embed`, `archive/zip`, `crypto/hmac`,
`crypto/rand`, `go/ast` and `go/parser` for the vocabulary guards, the
official MCP Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.7.0) for
`skill.install` and for driving the genre transcripts over the real
transport, `internal/testutil` for the ephemeral database.

**Prerequisite:** `docs/superpowers/plans/2026-08-31-core.md`,
`2026-08-31-metamodel.md`, `2026-09-02-markdown.md` and
`2026-09-02-views.md` are implemented and landed. This plan is written
against **the code that shipped**, read out of `internal/web/mcp.go`,
`internal/web/mcp_metamodel.go`, `internal/web/mcp_views.go`,
`internal/web/mcp_docs.go`, `internal/web/auth.go`,
`internal/web/export_test.go`, `internal/metamodel/schema.go`,
`internal/metamodel/bulk.go`, `internal/metamodel/relation_types.go`,
`internal/views/renderers.go` and `internal/views/predicate.go` on
2026-09-06. Forty-four tools are registered today and every identifier
quoted below was read from those files, not from the specs.

**Source spec:** `docs/superpowers/specs/2026-09-02-agent-skill-bundle-design.md`,
roadmap item 7 of `docs/superpowers/specs/2026-08-31-core-and-metamodel-design.md`.

## Before the first task: the line, and how a crossing of it is caught

Read this section once. It is the whole sub-project. Every task below is
an application of it, and a task that cannot be judged against it has
been written wrong.

### The problem, stated exactly

A skill bundle is prose that teaches an agent how to use a surface. The
tool descriptions are **already** prose that teaches an agent how to use
the surface, and they are not a rough draft of one: `views.upsert`'s
description carries the renderer catalogue generated from
`internal/views/renderers.go`, the operator table generated from
`internal/views/predicate.go`, the layout modes generated from
`views.LayoutModes()`, and about six thousand characters of hand-written
rules that exist because a review round found an agent would otherwise
meet an empty picture. `types.upsert` carries `versionClaimDoc`.
`relation_types.upsert` carries `quotedList(metamodel.SemanticRoles)`.

If the bundle restates any of that, it becomes a second copy of a
contract, and a second copy of a contract is the defect this repository
produced about twenty times in the last sub-project alone. The bundle is
worse than the average instance of that defect, because it is the one
artefact that ships **detached from the code** — installed to a skills
directory months before the server it describes is next upgraded — and
an agent reading it has no way to tell that it has gone false.

### The line

> **A tool description teaches one call. A skill page teaches what spans
> calls: a sequence, a decision taken before any call, or a consequence
> that only appears later.**

That is the principle. On its own it is not judgeable, so here is the
operational form, which is what the guards in Task 3 enforce and what
every review of this sub-project judges a sentence against:

> **The one-tool test.** A sentence that names exactly one registered
> tool and makes a claim about that tool's arguments, admitted values,
> defaults, bounds or refusals belongs in that tool's description. The
> bundle may **route** to it and may **quote** it verbatim with
> attribution; the bundle may not **restate** it.

Three worked judgements, so the line is concrete:

| Sentence | Where it belongs | Why |
|---|---|---|
| "`entities.upsert` takes at most 500 items and refuses a larger batch rather than clamping it." | the description | one tool, one bound, one refusal |
| "Declare every type first, then every relation type, then write entities in batches, then wire relations — because a relation whose endpoint types are not yet declared is refused, and a batch that fails is a batch you resend." | the bundle | four calls and their order |
| "A reference to another entity is a relation. Always." | the bundle | a decision taken before any call exists to describe it |
| "`views.validate` returns a JSON pointer into your document." | the description | one tool, one return |
| "Validate, read the pointer, fix that position, validate again — two iterations is normal and is not a sign you are doing it wrong." | the bundle | a loop over one tool, which the tool cannot describe from inside itself |

The fourth and fifth rows are the interesting pair, because they are
about the same tool. The description says what one call answers; the
bundle says that you are expected to make the call more than once. A tool
cannot tell you that calling it twice is the normal case, because from
inside one call there is no second call.

### The corollary the bundle is built on

**Where the surface already generates a table, the bundle links to it and
enumerates nothing.** The bundle contains no operator table — `views.run`
and `views.validate` both carry `views.OperatorDescription()` on the
wire. It contains no renderer parameter list — `views.upsert` carries
`views.RendererDescription()`. It contains no list of layout modes, no
list of document kinds, no restatement of `versionClaimDoc`.

`reference/queries.md` is therefore **not** a copy of the query language.
It is the four things the generated tables cannot say: that the language
is worth learning at all, in what order to build a document, that the
compose loop is a loop, and which of its failure modes are *silent* —
which is the one property no single call's description can report,
because a silent failure returns success.

### How a crossing is caught, in both directions

Discouragement is not a mechanism. Four guards, and each catches a
different direction of drift. All four are stated with their assertions
in Tasks 2, 3 and 4; this is the map.

1. **Generation.** `reference/tools.md` is generated from the registered
   tool table and committed. A tool added, renamed or removed without the
   file moving fails `TestToolReferenceIsCurrent`. Direction caught:
   *the surface moved and the bundle did not.*
2. **The anti-restatement guard.** Every sentence in the bundle that
   names exactly one registered tool and carries a claim marker must be
   inside an attributed quote block whose body is a **verbatim substring
   of that tool's registered description**. Direction caught, twice
   over: *the bundle invented a claim* (no matching description) and *the
   description was reworded* (the quote stops matching). This is the
   guard that makes the line above a rule rather than an aspiration.
3. **Vocabulary blocks.** Every closed vocabulary the bundle names lives
   in a delimited `vocab:` fence and is set-compared against its single
   Go declaration. Direction caught: *a seventh field type, an eighth
   semantic role, a fifth renderer.*
4. **Executed transcripts.** Every genre example is applied against an
   ephemeral database **over the real MCP transport**, and its shape is
   asserted afterwards through `games.counts`. Direction caught: *an
   example that no longer runs.*

And one that is not drift but its mirror image, and matters as much:

5. **The tripwire.** `recipes/seeding-a-game.md` teaches a
   read-then-write re-seed loop **because `on_conflict` is not on the
   surface yet** (see "Ship order"). `TestTheSeedingRecipeIsStillNeeded`
   asserts that `entities.upsert`'s registered description does not
   mention `on_conflict`. The day Task 10 of the metamodel plan lands,
   that test goes red and the recipe is rewritten. Direction caught: *the
   surface gained a capability and the bundle went on teaching around
   it* — which is the failure the four guards above are all blind to,
   because nothing in the bundle became false, it merely became bad
   advice.

### Ship order: what this plan does not ship, and why the omission is enforced

The spec's §8.6 rule is that **a page describing an unimplemented surface
must not exist** — not as a stub, not as "coming soon". Two surfaces the
spec's bundle tree names are not implemented today:

- **The analysis engine.** `internal/analysis` does not exist, no
  `analysis.*` tool is registered, and `analysis_traits` is not a column.
  So this plan ships **no `reference/analysis.md` and no
  `recipes/auditing-a-design.md`**, and the fourth modelling law is
  written as it can be stated today: `semantic_role` at declaration time,
  with a one-line note that a second, analytical axis is coming and that
  declaring the role now is what makes it cheap. `modelling/deciding.md`
  keeps decision 2 — one relation type with a field, or two types — but
  argues it from *querying* and from what an edge means to a reader,
  because arguing it from `analysis_traits` would be arguing from a
  column that does not exist.
- **`on_conflict` on the bulk upserts.** Decided (core open question O2),
  filed as Task 10 of `docs/superpowers/plans/2026-08-31-metamodel.md`,
  not implemented. See the tripwire above.

Both omissions are enforced rather than remembered:
`TestNoBundlePageNamesAnUnregisteredTool` reads every tool-shaped token
in every bundle file and fails on one the server does not register, so a
page mentioning `analysis.cycles` cannot be committed.

### What changed since the spec was written, and which the bundle must teach as it is now

The spec is four days old and three of its statements have been overtaken
by shipped code. The bundle teaches the current truth.

- **Types can be renamed.** `types.rename` and `relation_types.rename`
  are registered, take `from` (the current key, matched
  case-insensitively), `to`, and a required `expected_version`. The views
  plan closed with "there is still no rename operation" and that sentence
  is now false. **The bundle must not teach the workaround the old
  surface forced** — delete-and-recreate, which loses every edge — and
  must teach what a rename costs instead: saved views that named the old
  key go **stale but keep running**, and report the position in their own
  query document that drifted.
- **Entity keys are still permanent.** There is no `entities.rename`. A
  row's own key is chosen once. This asymmetry is exactly the kind of
  thing an agent will get wrong in the safe direction (assuming nothing
  can be renamed) and the expensive direction (assuming everything can),
  so `modelling/naming.md` states both halves and Task 7's guard pins
  both.
- **`games.counts` exists.** The spec's §10.4 — "there is no cheap way to
  learn a game's shape" — is resolved. One call returns a row per entity
  type and per relation type with its count and its invalid count, which
  is precisely what `recipes/joining-a-game.md` needed and could not
  have. The recipe is written around it and is three calls, not ten.

### The two standing lessons, applied to a documentation sub-project

**A rule established correctly and not carried one step along.** This
arrives here in a specific shape: a guard that reads *some* of the
bundle. Every guard in this plan enumerates the bundle from
`skill.Files()` and walks **every file**, including `skill.md` itself,
including the genre `.json` files, including any file a later contributor
adds. A guard with a hardcoded list of pages is the same defect as
`walkStrings` missing a promoted field, and each task below says which
mutation proves its guard walks the whole tree.

**Correct and unasserted.** For every fact a task gets right, the task
names the test that goes red if it were wrong, and the step that breaks
the code and watches it fail. A guard is the easiest thing in this
repository to write green-forever: a regexp that matches nothing passes
every input. Every guard in this plan therefore has a **precision
fixture** — a hand-written string that it must find a hit in, and a
hand-written string that it must not — asserted in the same test. That
requirement is not decoration. Task 9's denylist scanner would otherwise
match `request` as `quest` and be disabled by the first contributor who
hit the false positive.

### `TEST_DATABASE_URL` must be exported

Unchanged from every plan before this one, and it bites Task 8 hardest,
because a transcript test that skips is a transcript test that has never
run an example:

```bash
export TEST_DATABASE_URL='postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable'
go test ./internal/db/ -run TestMigrationsApply -v
```

Expected `--- PASS`, not `--- SKIP`.

anti-restatement guard in `internal/skill` will find an import cycle and
should not solve it by copying the tool list.

### Task 1: The bundle package, its hash, and the budgets that keep it readable

**Files:**
- Create: `internal/skill/skill.go`
- Create: `internal/skill/zip.go`
- Create: `internal/skill/zip_test.go`
- Create: `internal/skill/budget_test.go`
- Create: `internal/skill/files/skill.md` (placeholder, replaced in Task 5)

The package exists before any prose does, because the budget guard is
what stops `skill.md` becoming 325 lines, and a budget applied after the
page is written is a budget that gets raised.

- [ ] **Step 1: The package**

`internal/skill/skill.go`:

```go
// Package skill holds the agent skill bundle: the prose that teaches an
// agent to use Maestro's tool surface, embedded in the binary and served
// as a zip.
//
// **This package holds no contract that a tool description holds.** The
// bundle teaches what spans calls — order, judgement, consequence — and
// routes to the descriptions for everything a single call can state
// about itself. internal/web/skilldoc_test.go enforces that in both
// directions; see the plan section "the one-tool test".
//
// It imports nothing from internal/web, and it must not: web imports
// this package to register skill.install, so the dependency has one
// direction. Guards that need the registered tool table live in
// internal/web and read the bundle through Files().
package skill

import (
	"embed"
	"io/fs"
)

//go:embed files
var embedded embed.FS

// Files is the bundle as it ships, rooted at the bundle's own top level:
// "skill.md", "reference/errors.md", "genres/mmorpg.json".
//
// It is exported for the guards. Every one of them walks this tree with
// fs.WalkDir rather than naming pages, so a page added tomorrow is
// covered without editing a test — the failure mode the last sub-project
// hit nine times was a rule that watched the files it was written for.
func Files() fs.FS {
	sub, err := fs.Sub(embedded, "files")
	if err != nil {
		// Unreachable: the embed directive above is what creates the
		// directory this reads, so a failure here means the binary was
		// built from a tree with no bundle in it.
		panic("skill: embedded bundle is missing: " + err.Error())
	}
	return sub
}
```

- [ ] **Step 2: The deterministic zip and the version hash**

`internal/skill/zip.go`. Two properties matter and both are asserted:
the zip is byte-identical across builds of the same tree (so
`bundle_version` is a cache key an agent can trust), and the hash is
**length-prefixed** per path and per body, so no two different trees can
hash the same by concatenation.

```go
// Zip renders the bundle as a zip archive. Entries are written in sorted
// path order with a zeroed modification time, so the same tree produces
// the same bytes on every build and the same bundle_version on every
// process — an agent's "I already have this one, skip the download" is
// only worth anything if that holds.
func Zip() ([]byte, error)

// Version is the bundle's content hash: "sha256:" followed by hex.
//
// It hashes the *tree*, not the zip, and it length-prefixes every path
// and every body before hashing them. Without the prefixes, a file
// "ab" holding "c" and a file "a" holding "bc" hash identically, which
// is the classic concatenation collision and is why Nottario's hash is
// built the same way. Computed once, lazily, under a sync.Once: the
// tree cannot change while the process runs.
func Version() string
```

- [ ] **Step 3: `internal/skill/zip_test.go`**

- `TestTheZipIsByteIdenticalAcrossCalls` — `Zip()` twice, `bytes.Equal`.
  **Mutation:** set the entry `Modified` field to `time.Now()`; the test
  must fail. A zip built with the archive's default header carries a
  timestamp and this is not hypothetical.
- `TestTheVersionHashIsLengthPrefixed` — build two in-memory trees,
  `{"ab": "c"}` and `{"a": "bc"}`, hash both with the same unexported
  helper `hashTree(fs.FS)`, assert the hashes **differ**. **Mutation:**
  drop the length prefixes from `hashTree`; the test must fail. This is
  the assertion that would be missing if the test only checked that the
  real bundle hashes stably, which is true under a broken hash too.
- `TestTheVersionMovesWhenOneByteMoves` — hash the real tree, then hash
  an overlay `fs.FS` with one byte appended to `skill.md`, assert the
  hashes differ.

- [ ] **Step 4: `internal/skill/budget_test.go`**

`TestEveryBundlePageFitsItsTier`, one sub-test per file, walking
`Files()` with `fs.WalkDir` so a new page is covered without editing it:

| Tier | Match | Lines | Bytes |
|---|---|---|---|
| entry point | `skill.md` | ≤ 170 | ≤ 9000 |
| reference, modelling | `reference/*.md`, `modelling/*.md` | ≤ 250 | ≤ 14000 |
| genres, recipes | `genres/*.md`, `recipes/*.md` | ≤ 300 | ≤ 17000 |
| transcripts | `genres/*.json` | — | ≤ 60000 |

The byte caps are there because the line caps alone are gameable by a
page of very long lines, and the number an agent actually pays is tokens,
for which bytes are the honest proxy. 9000 bytes is roughly 2,000 tokens
at this repository's measured 4.4 bytes per token for English prose with
code fences.

`TestEveryBundleFileIsInATier` — the same walk, asserting every file
matched exactly one tier. **This is the guard on the guard**, and it is
the "one step along" lesson in its purest form: without it, a
contributor adding `advanced/analysis.md` gets a 4,000-line page and a
green suite, because the tier table did not name their directory. Its
**mutation:** add a file at `internal/skill/files/notes.txt` in a scratch
overlay and assert the test reports it as untiered.

- [ ] **Step 5: See them red**

Raise `skill.md` above 170 lines with a scratch copy, run
`go test ./internal/skill/ -run TestEveryBundlePageFitsItsTier`, watch it
fail naming the file and the count, restore.

**Corrections from implementing Task 1** (every mutation below was
applied to the shipped code, verified present in the file, and watched
fail the test that claims it, then reverted).

1. **`TestTheZipIsByteIdenticalAcrossCalls` does not catch the mutation
   the plan gave it.** The plan's step 3 says "set the entry `Modified`
   field to `time.Now()`; the test must fail". It does not: the zip
   format stores a DOS timestamp with **two-second granularity**, so two
   calls to `Zip()` in the same process, microseconds apart, produce
   byte-identical archives even with the build clock in every header.
   The mutation was applied and the test stayed green — a test that
   passes for the wrong reason, and one that reads as though it pins
   reproducibility across builds while pinning only that a pure function
   is pure. What ships adds `TestTheZipCarriesNoBuildTimestamp`, which
   reads the archive back and asserts every entry's stored modification
   time is the zip zero stamp (decoded year ≤ 1980) rather than a real
   clock. The same mutation fails that test naming the entry and the
   date. The byte-equality test is kept, because it is what catches
   non-determinism with no clock in it — map iteration order in the
   walk, for instance.
2. **The hash covers the tree; the agent is served the archive; the
   equivalence is now asserted rather than assumed.** `Version()` hashes
   the tree, as the plan specifies, which is only honest while the zip
   holds exactly that tree. Two tests pin it: `TestTheZipHoldsExactlyTheTree`
   reads the archive back and compares it entry by entry against the
   walk, and `TestTheVersionMovesWheneverTheZipDoes` partitions six
   mutated trees (byte appended, byte removed, file removed, file added,
   file renamed, unchanged) by archive bytes and by version and asserts
   the two partitions agree. **Mutation:** make `zipTree` skip paths
   ending in `.md`; the second test reports nine offending pairs and the
   first reports the missing entry, while the hash goes on moving for
   trees whose served bytes no longer differ.
3. **The budget guard reports a problem for an empty tree, and for a
   tree with no `skill.md`.** Every assertion over `auditBudgets` is of
   the form "it found nothing wrong", which is also what a walk that
   read no files reports. `auditBudgets` therefore records an overrun
   itself when the walk saw zero files, and a second one when no file
   matched the entry-point tier, and `TestTheBudgetGuardFailsOnAnEmptyTree`
   drives both. **Mutation:** delete the zero-files branch; that test
   fails with "an empty bundle passed the budget guard". The
   no-`skill.md` half of it needs a fixture holding *some other* page —
   today the bundle is one file, so deleting `skill.md` produces the
   empty tree and would have been caught by the wrong branch.
4. **The untiered guard's mutation is asserted in the test rather than
   run by hand.** `TestEveryBundleFileIsInATier` audits an in-memory
   overlay carrying `notes.txt` and requires it to be reported, so the
   plan's step-4 mutation is re-run on every build instead of once by
   the author. The same shape covers both caps in
   `TestTheBudgetGuardCatchesAnOversizedPage`: a 200-line-taller
   `skill.md` for the line cap, and one 20,000-byte line for the byte
   cap, which is the cap the line cap alone cannot enforce.
5. **Plan step 5 was run against the real file as written**: 200 lines
   appended to `internal/skill/files/skill.md`, then
   `go test ./internal/skill/ -run TestEveryBundlePageFitsItsTier`,
   which failed with `skill.md: 214 lines, over the "entry point"
   tier's cap of 170`. Restored by copying the file back from a
   scratch copy.

### Task 2: The generated tool reference

**Files:**
- Create: `internal/web/skilldoc.go`
- Create: `cmd/maestro-skilldoc/main.go`
- Create: `internal/web/skilldoc_test.go`
- Create: `internal/skill/files/reference/tools.md` (generated)

`reference/tools.md` is the bundle's index of the surface. It is
**generated from the registered tool table and from nothing else**,
which is the `sqlc diff` pattern already in `make check`: generated
artefact committed, test red when the source moved and the artefact did
not.

What it contains is deliberately narrow: **one line per tool, its name
and the first sentence of its registered description**, grouped by
prefix. Not the full descriptions. The full descriptions are on the wire,
where an agent gets them for free with the tool list; copying six
thousand characters of `views.upsert` into a file an agent must read
separately is paying twice for one text and creating the drift this
sub-project exists to prevent. The file's job is *routing* — "there are
forty-four tools, here they are by domain, here is the one you want" —
which the wire's flat alphabetical list does not do.

- [ ] **Step 1: `internal/web/skilldoc.go`**

```go
// ToolReference is the bundle's reference/tools.md, generated from the
// tools this server registers and from nothing else.
//
// **It carries first sentences, not descriptions.** The full text of
// every description is already on the wire in the tool list an agent
// receives at connect time; a second copy in a file would be the drift
// this whole sub-project is built to refuse, and it would cost an agent
// the same tokens twice. What the wire does not give is grouping and a
// one-line answer to "which of these forty-four do I want", which is
// what this file is.
//
// TestToolReferenceIsCurrent regenerates this in memory and diffs it
// against the committed file, so a tool added, renamed or removed
// without regenerating fails the build.
func (s *Server) ToolReference() string
```

It walks `s.mcpToolDescriptions` — already recorded by `addScopedTool`
for exactly this class of reader — sorts by name, groups on the prefix
before the first `.` (with `whoami` in a `session` group), and emits:

```markdown
<!-- generated by cmd/maestro-skilldoc; do not edit -->
# The tool surface

Forty-four tools. Each one's full contract — every argument, every
admitted value, every refusal — is in its own description, which your
client already has. This page is the index: what exists, and which
domain it belongs to.

## entities

- `entities.get` — Read one entity by its address — its type's key plus its own key — with its fields.
- `entities.list` — …
```

The count in the header is written by the generator from `len(...)`, not
by hand. A hand-typed "forty-four" is a sentence that goes false on the
forty-fifth tool with nothing to catch it.

- [ ] **Step 2: `cmd/maestro-skilldoc/main.go`**

Builds a `Server` with the same registrations the real binary makes
(`NewServer` with a `MCPDeps` whose services are non-nil stubs — the

```go
// bundleSentence is one sentence of one bundle page, with the position
// that lets a failure say "modelling/naming.md:41" rather than "somewhere
// in the bundle".
type bundleSentence struct {
	Path string
	Line int
	Text string
	// InQuote is true when this sentence sits inside an attributed quote
	// block (see quoteAttribution), which is the one place a claim about a
	// single tool is allowed.
	InQuote  bool
	QuoteFor string // the tool the block is attributed to
}

// scanBundle splits every file of the bundle into sentences.
//
// It walks fs.WalkDir over the whole tree — not a list of pages — for the
// reason every guard in this package does: a rule that watches the files
// it was written for stops watching the moment somebody adds one.
// Markdown list items, table cells and heading lines are sentences too;
// a claim does not stop being a claim for being a bullet, and the first
// draft of this guard split on ". " alone and saw none of them.
//
// JSON files are scanned as well, through their string values only, so a
// genre transcript that grew an explanatory "_comment" restating a bound
// is caught by the same rule as a markdown page.
func scanBundle(t *testing.T, fsys fs.FS) []bundleSentence
```

- [ ] **Step 2: `TestTheBundleRestatesNoToolDescription`**

# Maestro skill

Maestro records the **content design** of a game: what a player can be,
where they can go, what they can do and what they unlock. It is not a
task tracker and there is no kanban here.

Maestro ships **no built-in game vocabulary**. There is no Quest, no
Zone, no Class, no Circuit. A game declares its own, and that is the
product rather than a gap. You will declare a vocabulary before you can
write anything, and the shape you choose is the thing that is expensive
to change later.

## 1. Identify yourself

Call `whoami` first. It answers who you act for and **which single game
your token is bound to**; `project_slug` is that game's address, and it
is the value every other tool's optional `game` argument is checked
against.

One token, one game. A `scope_violation` is not a bug to route around —
it is the answer to a request that names a different game. Ask the human
for the right token.

`whoami` also reports `skill_bundle_version`. If it differs from the
version in the manifest beside these files, run `skill.install` and
restart your host application before doing anything else: the pages you
are reading were written for a different server.

## 2. The four primitives

| Primitive | What it is | Declared with |
|---|---|---|
| **EntityType** | a kind of thing this game contains | `types.upsert` |
| **Entity** | one instance of a kind | `entities.upsert` |
| **RelationType** | a kind of directed edge between things | `relation_types.upsert` |
| **Relation** | one edge between two entities | `relations.upsert` |

Everything else in Maestro — catalogues, place graphs, mission lists with
their preconditions, progression trees — is a **view** over those four.
There is no fifth primitive and no built-in notion of a quest.

Every field an entity or an edge carries is one of these types, and there
are exactly six:

```vocab:field_types
text longtext number bool enum list<text>
```

There is no reference type. That is law 1.

## 3. The four laws

Stated flat here because you need them before your first `types.upsert`.
Argued, with what each one costs when broken, in `modelling/deciding.md`.

1. **A reference to another entity is a relation. Always.** A quest's
   zone is not a `text` field holding a zone's key. It is an edge. The
   day someone wants the map, a text field cannot be traversed and the
   repair is one write per row.
2. **Data that belongs to the connection goes on the connection.** Edges
   carry their own declared fields. A door's required ability belongs on
   the edge, not on either room.
3. **Declare the direction when you declare the relation type, and name
   the type so it reads source → target.** `takes_place_in`,
   `available_to`, `unlocks`, `connects_to`. Queries take direction
   literally and infer nothing.
4. **Say what an edge means at the moment you declare it**, with
   `semantic_role`. Not later. Six months on, re-deriving what thirty
   relation types meant is a job nobody does correctly, and a second,
   analytical axis is coming that will be read off exactly this
   declaration.

## 4. Keys are the API

- Everything is addressed by **key**; a game is addressed by **slug**.
- Keys are matched **without regard to case**. `Quest` and `quest` are
  one key, and writing the second when the first is stored is refused,
  naming both spellings, rather than quietly updating the row.
- **An entity's own key is permanent.** Choose it from something that
  will not change — not from a display name a writer will rewrite.
- **An entity type's key and a relation type's key can be changed**, with
  `types.rename` and `relation_types.rename`, addressed by the key it has
  now. Saved views that named the old key keep running and report what
  drifted, at the position in their own query document.
- Two spelling rules, not one, and they differ because the mechanisms
  differ: a **field** key is `^[a-z][a-z0-9_]*$`, a key that addresses a
  **row** is `^[A-Za-z0-9][A-Za-z0-9_-]*$`. Both capped at 64, both
  ASCII. `modelling/naming.md` has the reason and the rest of the rules.

The choice of language for a game's keys is **the game's**, not
Maestro's. A Spanish studio's `mision` is as correct as `quest`. Both
rules are ASCII, so `misión` is not a legal key — that is the
case-folding index talking, not a preference about language — and
consistency within one game matters more than which language it is in.

## 5. The seeding loop

In this order, because each step is what the next one is checked against:

1. `types.upsert` — every entity type, with its field schema.
2. `relation_types.upsert` — every relation type, with its endpoint type
   keys and its `semantic_role`. An edge whose endpoint types are not yet
   declared is refused.
3. `entities.upsert` — in batches, per type.
4. `relations.upsert` — in batches, once both endpoints exist.
5. `games.counts` — read the shape back and check it is what you meant.

**Every write is versioned.** Send `expected_version` on every update,
matching the version you read. A mismatch is `version_conflict` and
carries what is current: re-read, merge, retry. Do not retry blind.

**A version claim is a claim about a row that exists.** Claiming one for
a row this game does not have is refused, and is never a quiet
re-creation.

**Batches are bounded and the bound is refused rather than clamped.** A
batch over the limit fails as a batch; it does not silently write a
prefix. Split it yourself.

Full sequence, with re-seeding: `recipes/seeding-a-game.md`.

- [ ] **Step 1: `reference/fields.md`**

The six rules an agent gets wrong, none of which is a single tool's
contract — every one of them is a property of *the validator* that shows
up across `types.upsert`, `entities.upsert`, `relation_types.upsert` and
`relations.upsert` alike, which is why they belong here:

- An unknown field is an error. It is never silently dropped, and a
  schema change flags the rows that stopped fitting rather than deleting
  them or filling them in.
- An absent optional field with no default stays absent. It is not
  zero-filled, and a query asking `exists` will tell you so.
- **A default is declared by the presence of the `"default"` key and by
  nothing else.** There is no `has_default` input: it is a Go-side flag
  and never crosses the wire. Sending it gets you silence — the key is
  ignored and no default is declared. This is what makes a default of
  `false` or `0` behave like any other default. An explicit
  `"default": null` declares **no** default.
- `required` together with a default is rejected. The default lands
  before the field could be reported missing, so the pair makes
  `required` unreachable.
- Field keys are `^[a-z][a-z0-9_]*$`, at most 64 characters. Row keys are
  a different, wider rule; `modelling/naming.md` says why.
- Labels, colours and icons are validated too, and their problems come
  back **together** with any key problem in the same answer: one pass,
  one round trip. `label` is required; `color` is a CSS hex colour in one
  of four forms and nothing else; `icon` is a lower-case name, not an
  image and not an emoji. Caps are counted in runes, so an accented label
  is not shorter than an unaccented one.

Plus the `vocab:field_types` fence, and one paragraph per type on what it
buys you *later* — which is the part no description can say, because the
cost lands in a different call:

> layered view and cannot be a timeline axis. Every one of those is a
> different tool, months later, and none of them can tell you that the
> mistake was made at declaration time.

- [ ] **Step 2: `reference/errors.md`**

A table of **code → what actually happened → the next call to make**,
carrying the `vocab:error_codes` fence. The page's whole reason to exist
is that three codes look alike and send you to three different places:

| Code | What happened | What to do |
|---|---|---|
| `invalid_schema` | a type declaration cannot stand | fix the declaration, re-issue `types.upsert` |
| `schema_violation` | a row of values does not fit a declaration that can | fix the row's fields, re-issue the upsert |
| `invalid_input` | the call's own arguments are malformed — a key, a label, a colour, an icon | fix that argument, re-issue the same call |
| `version_conflict` | somebody wrote between your read and your write | re-read, merge, retry with the returned version |
| `not_found` | including a version claim for a row that is gone | re-create deliberately, without a version claim |
| `in_use` | a removal would strand content | cascade deliberately, or remove the content first |
| `query_stale` | the design moved under a saved view | repair the view; do not switch the stale policy to make the message go away |
| `retryable` | a bounded operation ran out of budget | narrow it — the message names which bound |

Every one of these reports **every problem it can see at once**. Fix them
in one pass. An agent fixing one typo per round trip on a 200-row seed
pays 200 round trips for one bad afternoon.

The three-way split is the page's headline, because the recovery for a
key with a space in it is `invalid_input` — and an agent that reads it as
`schema_violation` goes looking at entity values, which is exactly the
wrong place.

- [ ] **Step 3: `reference/queries.md`**

4. **Staleness is the normal case**, not a broken view. A view written

- [ ] **Step 1: `modelling/deciding.md`**

The four laws, argued, each with its cost stated in calls.

**Decision 1 — field or relation?** The rule: *if any other entity in
this game is, or could plausibly become, the same thing this value names,
it is a relation.*

- `min_level: 22` on a quest is a field. `22` is a number, not a thing
  the game will have a row for.
- `zone: "elwynn"` on a quest is a **relation**. The fact that it is
  spelled like a string is the whole trap.

Worked, with the cost:

> **Before.** You declare `quest` with `{"key": "zone", "type": "text"}`
> and seed 300 quests. Every write validates. Every row looks right in a
> table. Filtering the listing by `zone = "elwynn"` even works.
>
> **Three hundred entities later.** A designer asks for the quest map
> coloured by zone. A traversal walks relations; it cannot follow a text
> field. There is no relation type to name. Deleting a zone leaves 40
> quests pointing at a key that resolves to nothing, and nothing tells
> anyone.
>
> **The repair is not a migration.** Declare `zone` as a type, seed the
> zones, declare `takes_place_in`, read all 300 quests back, write 300
> relations, then remove the field — which touches all 300 rows again,
> because an unknown field is an error and not a silently dropped key.
> Six calls become six hundred.

And the inverse mistake, so the rule does not over-apply: modelling
`min_level` as a relation to a `Level` entity gives you sixty
content-free rows and no way to ask for "quests between level 20 and 30"
without a traversal, because the range operators are number operators and
there is no number left.

**Decision 2 — one relation type with a field, or two types?** The rule
today: *if the two edges would ever be walked, counted or drawn
separately, they are two types; if they differ only in something a human
reads, one type with a field.* A `requires` type carrying
`kind: enum[hard, recommended]` is one edge as far as every traversal is
concerned, and every future question of the form "what actually gates
this" has to filter it out by hand, in every query, forever. Two types
cost one extra `relation_types.upsert`.

The counter-example, on the same page, so the rule does not become "two
types always": a metroidvania's `connects_to` carrying
`requires_ability: text` is **one** type. Gated and ungated doors are the
same spatial edge, they walk the same way, and a predicate on the edge's
own field separates them at query time. The difference between the two
cases is whether the distinction changes how the graph is *walked* or
only which edges are *selected*.

> A note this page carries and must keep: a second, analytical axis on
> relation types is coming, and it will be read per relation type. When
> it lands, this decision gains a sharper form — two edges that must be
> analysed differently cannot share a type — and the shape above is
> already the right one. Declaring `semantic_role` now is what makes that

- [ ] **Step 2: `modelling/naming.md`**

Keys are the API: every saved view, every route and every reference names
them as text.

- **Entity type keys are singular**: `quest`, not `quests`. The plural
  has a home in `label_plural`. This is a *bundle* convention — the
  server accepts either — and it is stated as one.
- **Lower snake is the bundle's default spelling, not the server's rule.**
  The server accepts `quest`, `Quest` and `quest-line` alike; it refuses
  `main quest 1` and `misión-01`. Within one game, pick one and keep it,
  because keys are matched case-insensitively and the second spelling is
  refused rather than applied. A game whose own handles capitalise —
  `Elwynn_Forest`, `GP_Monaco` — should do it everywhere.
- **What the row-key rule excludes earns its place**: no dot, slash,
  space or percent, so a key drops into a URL path and a query token
  without escaping; no leading punctuation, so no key reads as a flag;
  ASCII only, because case folding is not Unicode normalisation and two
  normalisations of one accented word would otherwise be two keys.
- **Relation type keys are verb phrases that read source → target.**
  Direction is literal in a query; a name like `zone_link` forces every
  future query author to look the type up and guess.
- **Never declare a field named `name`, `key`, `type` or `created_at`.**
  It is legal and nothing breaks — the built-ins stay reachable through
  their own sigil — but every predicate in the game becomes ambiguous to
  a human reader.
- **Numbers are `number`, ordered categories are `enum` with the options
  in order.** Both costs are invisible on the day of the write and total
  on the day of the diagram.
- **What can be renamed, and what cannot.** An entity's own key is
  permanent: there is no rename for a row, and the address an upsert
  writes against is the one it was created with. An entity type's key and
  a relation type's key **can** be changed, addressed by the key they
  have now, and the type keeps its id and every edge. What it costs: a
  saved view that named the old key goes stale, keeps running, and
  reports the position in its own query document that drifted. Repairing
  it is a `views.upsert` from a document you already hold.

  Which is why the useful habit is not "never rename" — it is: **derive
  an entity's key from something that will not change**, and treat a type
  rename as a small, visible cost rather than an impossible one.

- [ ] **Step 3: `modelling/mistakes.md`**

Before/after pairs, each with the repair counted in calls. The zone one
from decision 1, the two-vocabularies-in-one-type one from decision 2, a
key derived from a display name that got rewritten, a level stored as
text, and the one an agent hits first: **running a shape check on a
half-seeded game.** A game mid-seed is *supposed* to look like a field of
disconnected rows, and reading anything into that before the edges are
written is a self-inflicted wound.

- [ ] **Step 1: `recipes/seeding-a-game.md`**

The order, the batching, and the honest re-seed.

The order is laws-driven and stated as such: types, then relation types
(whose endpoint keys are checked against the types), then entities in
batches, then relations (whose endpoints must exist), then `games.counts`
to read the shape back.

Batching: split by the bound, never send a batch you have not counted,
and note the property that matters across calls — **a batch is refused as
a batch**, so a failure means you resend the batch, not that you go
looking for which prefix landed.

**The re-seed, written honestly:**

> **Re-running a seed is not free today.** Every write is a
> compare-and-set, so a second run of the same payload conflicts on every
> row that already exists — that is the versioning working, not a bug.
> Until the surface grows a conflict mode, a re-seed is:
>
> 1. `entities.list` the type, collecting key → version.
> 2. Send the same items back with each one's `expected_version`.
> 3. For a key the listing did not return, send it with no version claim:
>    it is new.
>
> Do not carry versions across a session boundary. Read them again; the
> listing is one call per type and you are about to make hundreds.

### Task 11: Delivery — `skill.install`, the signed zip, and the version handshake

**Files:**

Delivery follows the sibling project, which is the working precedent and

that costs its full price on every install, including the installs that

- [ ] **Step 1: The signing key — decided**

The sibling signs its download URL with the session signing key. Core's
Task 22 deleted Maestro's, correctly, on the grounds that it was a
phantom control. Three options were considered (spec §7.2); **this plan
adopts (a)**:

> A 32-byte key from `crypto/rand` minted at process start, held in
> memory, never configured and never persisted. A five-minute signed URL
> has no reason to survive a restart, and a multi-replica deployment is
> not something Maestro claims to support today.

It cannot become a phantom control, because it is generated by the code
that uses it and a process with no such code has no key. The day Maestro
grows replicas, option (c) — the ordinary bearer header — is the
documented fallback, and the reason it is not the choice today is that it
puts a game token into whatever `curl` invocation the agent constructs,
which is a token in a shell command in a transcript.

`server.go` gains the key and one comment saying exactly the above,
including the replica limitation, because "write down what a mechanism
does not do, in the code" is the fifth lesson of the last sub-project.

- [ ] **Step 2: `GET /skill.zip`**

Takes `exp` (unix seconds) and `sig` (hex HMAC-SHA256 over the path and
the expiry, with the process key). No bearer header, no cookie. Serves

- `TestAnExpiredSkillURLIsRefused` — sign with `exp` in the past.

## What this sub-project deliberately does not teach

Drawn explicitly so a later contributor does not drift across it, and so
that a later sub-project is not surprised by a gap.

- **It does not teach game design.** Nothing here says what makes a good
  quest, how long a progression should be, or how to pace anything. It
  teaches how to *record* a design, not how to have one.
- **It does not ship game content.** The transcripts are a dozen entities
  per type. Nothing in them should end up in a shipped game.
- **It does not restate a single tool's contract.** Every argument, every
  admitted value, every bound and every refusal stays in the description
  the wire already carries. Task 3 is what makes that a rule.
- **It does not enumerate the operator table or the renderer catalogue.**
  Both are generated into the descriptions of the tools that consume
  them. The bundle links and quotes, verbatim and attributed.
- **It teaches no analysis.** `internal/analysis` does not exist and
  `analysis_traits` is not a column. When the analysis sub-project lands,
  it adds `reference/analysis.md` and `recipes/auditing-a-design.md` and
  sharpens decision 2 of `modelling/deciding.md`; until then, a page
  naming an `analysis.*` tool is a failing build.
- **It teaches no conflict mode on the bulk upserts.** The seeding recipe
  teaches the read-then-write loop and carries a test that goes red the
  day the argument ships.
- **It adds no genre-specific server behaviour.** No template importer,
  no handler that reads a genre file, no tool named after a game concept.
  A transcript is applied by an agent, one ordinary call at a time,
  through the same tools any designer's agent uses. If applying a
  template is ever faster than doing it by hand for any reason other than
  typing, something has been built that should not exist.
- **It does not teach the web UI, the visual identity or how a renderer
  looks.** Sub-project 5 owns all of that. The bundle names renderers and
  stops.
- **It carries none of Maestro's own development workflow.** No tasks, no
  cycles, no commits, no git. Maestro is built against a different
  project's bundle and tracked there; the two bundles sit side by side in
  the same skills directory on the author's machine and any overlap
  between them is a bug.
- **It does not version per game and does not branch per host.** One
  embedded bundle, one hash, installed the same way everywhere. No
  overrides in v1.

## Open questions this plan does not close

1. **Replicas and the signing key.** Option (a) is adopted and is correct
   for a single process. A multi-replica deployment needs option (c) —
   the ordinary bearer header — and the day that becomes real, the
   trade-off is a token in a shell command. Recorded in
   `internal/web/server.go` beside the key.
2. **Whether the fourth-genre acceptance bar is worth its cost.** It is
   the only anti-ossification mechanism here that catches vocabulary
   smuggled into the templates, and it is human-judged, which makes it
   slow and slightly subjective. The alternative is trusting B1–B3, which
   are enforceable but only cover the code, not the teaching.
3. **`list<number>` and `list<enum>`.** There is one list type. An agent
   modelling "allowed difficulty tiers" gets `list<text>` and loses every
   enum operator and the validation that would have caught a typo. The
   bundle teaches around it today; it is small and cheap to add and the
   bundle would get shorter.
