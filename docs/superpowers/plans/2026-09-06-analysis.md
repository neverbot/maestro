# Maestro Analysis Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give a game four answers it cannot get by reading: where its prerequisites loop, what no player can reach, what nothing points at, and whether a named progression still holds. Plus the one declaration that makes all four possible on a metamodel that knows nothing about games — `analysis_traits` on a relation type — and one stored artefact, a **route**, that carries a verdict and knows when that verdict went out of date.

**Architecture:** One new domain package `internal/analysis`, one widening of `internal/graph`, one new column on `relation_types`, one new counter on `projects` maintained by database triggers, and two new tables. The three read-only analyses compute on demand inside a bounded read-only transaction and cache nothing. Cycles and unreachability compile into `graph.WalkCTE` — the same bounded, project-filtered, cycle-guarded walk `internal/views` compiles into — and the normalisation that turns a game's mixed `requires` / `unlocks` edges into one dependency direction rides in that walk's `EdgePredicate` rather than in a second emitter. Orphans are an aggregate with no recursion at all. Routes are their own rows, checked against the reachability closure, with `projects.design_version` as the staleness signal.

**Tech Stack:** Go 1.25.7, pgx/v5, sqlc for every static statement (the analyses' recursive SQL is emitted by `internal/graph` and therefore runs outside sqlc, exactly as `internal/views/compile.go` does), Postgres 16 (`text[]` with a `<@` check, statement-level triggers with transition tables, `WITH RECURSIVE`, composite foreign keys), the official MCP Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.7.0), `internal/paging` for the two cursor-paginated results.

**Prerequisite:** `docs/superpowers/plans/2026-08-31-core.md`, `2026-08-31-metamodel.md`, `2026-09-02-markdown.md` and `2026-09-02-views.md` are implemented and landed. This plan is written against **the code that shipped**, not against those plans' code blocks. Every identifier, signature, SQL snippet and constant quoted below was read out of `internal/graph/walk.go`, `internal/views/`, `internal/metamodel/`, `internal/paging/cursor.go`, `internal/web/mcp_views.go`, `internal/web/server.go` and `internal/db/migrations/` on 2026-09-06.

**Source spec:** `docs/superpowers/specs/2026-09-02-analysis-engine-design.md`, roadmap item 6 of `docs/superpowers/specs/2026-08-31-core-and-metamodel-design.md`.

## Before the first task

### `TEST_DATABASE_URL` must be exported

`internal/testutil`'s `NewPool` **skips** when `TEST_DATABASE_URL` is unset, and over 500 tests in this repository take a pool. With it unset, `go test ./...` prints `ok` for every package and asserts almost nothing.

```bash
export TEST_DATABASE_URL='postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable'
go test ./internal/db/ -run TestMigrationsApply -v
```

Expected `--- PASS`, not `--- SKIP`. If it says SKIP, nothing below this line is being verified.

### The two defects the last three sub-projects kept producing

Read `docs/superpowers/plans/2026-09-02-views.md`, "What this sub-project learned", once. Both defects it names are live risks here, and this plan is shaped around them.

**1. A rule established correctly and not carried one step along.** Named after the metamodel sub-project, and it arrived at least twenty more times in views — most often *inside the correction that established the rule*. The instances were not variations on a theme; they were the same shape: a guard that watched one file, a bound applied to a list of known fields rather than to the tree, an actor-column list extended in three places and one prefix short in each.

This sub-project's three highest-risk sites for it, named now so the fix is planned rather than discovered:

- **`design_version` must be bumped by every write to four tables.** The spec asks for it in Go, in the same transaction as the write. There are more than twenty such write paths across `internal/metamodel` and the bulk driver, and Task 1 puts the bump in **database triggers** instead, precisely because a Go call site is the thing this project keeps forgetting to add the twenty-first time. See Task 1's argument.
- **Traits reach four readers**: the coherence check on write, the resolver, the tool description, and the `semantics_source` map in every result. A trait added to the vocabulary and not carried into all four is the exact shape. Task 3 makes the vocabulary one table and asserts every reader against it **in both directions**.
- **The invalid-edge decision** (below) applies to four walks and one aggregate. Task 5 states it once and Task 8's orphan aggregate is where it would be forgotten.

**2. Correct and unasserted.** The most productive question views asked all sub-project: *for every assertion, name the mutation it is red under.* Whole classes of behaviour were right and pinned by nothing — `renderer_params` written and never read back, `pinned` stored and scanned as a default, `views.remove`'s entire answer being one boolean nothing checked.

So: **every test in this plan is seen red before it is trusted.** Each task's steps name the mutation. A test that was never red is a comment.

And, inherited verbatim from views because this engine is even more exposed to it: **every negative test asserts a non-empty positive control in the same test.** "No cycles were found" and "the walk returned nothing because the project filter was lost and the seed resolved to another game" are the same green. An analysis whose failure mode is an empty answer is this whole sub-project.

### The negative halves, listed once

The spec's four analyses each have an answer that means "nothing is wrong", and each of those is where a broken engine looks healthy. They are enumerated here so no task can ship without its half:

| Analysis | The negative half | The test that would fail if it were faked |
|---|---|---|
| cycles | an acyclic game reports zero cycles | `TestAnAcyclicGameReportsNoCyclesAndSaysHowManyEdgesItWalked` |
| unreachable | every entity is reachable | `TestAGameWhereEverythingIsReachableReportsZeroAndCountsThemAll` |
| orphans | every entity has an edge | `TestAGameWithNoOrphansStillCountsEveryEntityItConsidered` |
| routes | a route that holds | `TestARouteThatHoldsReportsOkForEveryStepAndNamesItsSeedSet` |
| all four | a game that declared nothing | `TestAnAnalysisOverAGameWithNoTraitsRefusesRatherThanReportingHealth` |

Each of those four positive-outcome tests asserts a **count of work done** — edges walked, entities considered, steps checked — and not merely an empty findings list, because an empty findings list is what a broken walk returns too. That is the plan's single most important structural rule and Task 12 checks all five at once.

### Invariants inherited, restated in each task

- **Isolation is enforced in SQL, not Go.** Every statement takes the resolved project id: `WHERE project_id = $1 AND lower(key) = lower($2)`, never by key alone; `WHERE project_id = $1 AND id = $2` for anything by id. In a recursive walk the filter appears in **both** terms — `internal/graph` already does this and asserts it as text; every seed this package writes filters as well, even though `graph`'s anchor join makes it redundant, and says in a comment that it is redundant today and defends the shape a later task adds.
- **Rows are addressed by key, games by slug.** Every MCP tool takes a key; every REST route is `/api/games/{game}/…` — which is what shipped, and **not** the `/api/g/<slug>/…` the spec's §9 writes. The spec is wrong about the prefix and Task 11 says so rather than inventing a second family of URLs.
- **Child-to-parent foreign keys are composite**, carrying `project_id`. `ON DELETE SET NULL` on a composite key **names its column**. Keys to `users` stay single-column. The spec's §6 DDL is illustrative and says itself that its keys are wrong; Task 1 writes them right the first time.
- **An upsert is a compare-and-set in SQL** under a `FOR UPDATE` read taken inside the same transaction, and **a version claim for a row that does not exist is refused**, not treated as a creation — `metamodel.RemovedError`, which satisfies `ErrNotFound`. Task 9 reuses that type rather than declaring a second.
- **Batches are bounded at five hundred items and refused rather than clamped.** `metamodel.MaxBulkItems` is 500 and is the precedent; a route's step list and a call's seed-key list each take the same bound with the same refusal. Page limits are the exception and are **clamped** (`paging.Size`), which is the existing split and not a new one.
- **Caller input is bounded before Postgres sees it**, reported as the caller's own argument at its own path.
- **Events publish after commit**, never inside the transaction, each stating its `minRole` and `humanOnly` as a decision with an argument. Only a deferred foreign key can distinguish a publish moved inside the transaction; Task 9 installs one in its own throwaway database, as `internal/views` and `internal/metamodel` both do.
- **Content routes register through `registerContentRoute`**, which applies the editor check to non-GET routes itself. `TestEveryContentRouteIsRegisteredAsContent` fails a route added with `mux.HandleFunc`.
- **Every negative test asserts the specific message and the specific path**, not merely that an error occurred.

## Decisions taken since the spec was written, and what they change here

Five decisions landed after 2026-09-02. Each one reaches this sub-project, and each is folded into the task that owns it rather than left as an amendment note.

**1. Relations carry `invalid` and `version` (migration 0009), judged by the rule entities are.** So anything that walks an edge must decide whether it follows a flagged one, and the two shipped answers disagree on purpose: `internal/views` **excludes** invalid edges from a picture unless `include_invalid` is set (`compile.go`'s `invalidFilter`, applied to relations as well as entities since 0009), and `internal/metamodel`'s traversal listing **follows** them, its `Invalid *bool` filter being a tri-state whose default is "both".

**This engine follows them, by default, like the metamodel and unlike views** — and the reasoning for the split is the whole point:

- `invalid` means *this row's `fields` no longer fit its type's `field_schema`*. It says nothing about the row's endpoints or its relation type, and **endpoints and relation type are the only things any analysis here reads.** So excluding invalid edges would let a field-schema edit on `requires` — adding a required `difficulty` field, say — make forty missions report as unreachable, with the cause being a change that has no relationship at all to whether they are reachable. A verdict about structure must not move when a field schema moves.
- Views excludes for the opposite and equally correct reason: a picture *asserts* a relationship, a reader believes the assertion, and drawing an edge whose own values are known-broken is a claim the game does not support.
- The orphan analysis has a sharper version of the same argument: an entity whose only edge is flagged invalid **is not an orphan**, and calling it one would send a designer to delete content that has edges.

The caller may ask for the stricter reading with `exclude_invalid: true`, and **every result reports `invalid_edges_followed`**, so a designer can see that the verdict rests partly on rows the metamodel has flagged. Silence there would be the "correct and unasserted" defect with the sign flipped.

**2. A type can be renamed, addressed by its old key** (`internal/metamodel/rename.go`). The lesson that file records is that a rename **moves the catalogue row and nothing else** — it deliberately does not tidy `view_refs.ref_key`, because the stored document and the dependency index agreeing on the *old* spelling is what makes resolution fall to the by-id arm and report `*_renamed` instead of `missing`.

Carried one step along, which is the instruction this project's standing defect exists to enforce: **a route step stores `entity_id` (the resolution path), plus `entity_type_key` and `entity_key` as a tombstone pair that a rename does not touch.** Task 9 writes that; Task 10 reports `type_renamed` on a check whose step resolves by id to a type whose key has moved; `TestARenameLeavesARouteStepSpellingTheOldKeyAndTheCheckReportsIt` is the test. Traits themselves are unaffected: they live on the `relation_types` row and are addressed by id everywhere the engine reads them.

**3. Rows are addressed by key and games by slug, everywhere.** Correcting the spec's §9 REST prefix, and deciding `routes.check`'s addressing: by **key**, not by id. The spec's §8 writes `routes.check` reading `WHERE project_id = $1 AND id = $2`; the id form does not exist on this surface. The isolation obligation is unchanged — the lookup filters on the project — and the mandatory test becomes `TestARouteKeyFromAnotherGameIsNotFound`.

**4. Batches are bounded at five hundred items, refused rather than clamped.** `routes.upsert` replaces a route's whole step list, so the step list is a batch: at most 500, and a 501-step route is `invalid_input` at `/steps` naming the count, not a route silently truncated to 500. `seed_entities` takes the same bound for the same reason.

**5. A version claim for a row that does not exist is refused.** `routes.upsert` with a non-zero `expected_version` against a route this game does not have answers `metamodel.RemovedError` — `not_found`, saying it was removed — and the reason is stronger for a route than for anything the error was written for: a route's `last_check`, its `last_checked_design_version` and every one of its step rows hang off the route's id, so a quiet re-creation would discard a verdict and an ordered walk somebody authored, under a new id, and answer success.

## Open questions settled to write this plan

The spec's §12 carries nine. Six block a task.

**O1 — `any` versus `all` gating. Settled: `any` is the default, `all` is available, and neither is stored.** The spec's argument stands and this plan adds one thing to it: the *asymmetry of cost* it names is a claim about which report a designer keeps reading, and this plan makes it checkable rather than believed. Task 6's `TestTheSameGameReportsFewerUnreachableUnderAnyThanUnderAll` asserts the direction of the difference on a fixture with one alternative route, and `TestUnderAllABothGatedEntityNeedsBothGatesReachable` pins that `all` is not silently `any`. Requirement *groups* stay out: they would live in the edge's field schema, which v1 deliberately does not read, and encoding groups in the trait vocabulary now is guessing their shape.

**O2 — should seed sets be stored objects? Settled: no new table, and routes are the answer when one is wanted.** The spec leaned this way and the schema makes it free: a route is an ordered list of entities in this game, which is exactly a seed set with an order nobody has to use. So `analysis.unreachable` takes `seed_route` (a route key) alongside `seed_entities` and `seed_entity_types`, and its steps become seeds. **What this buys is the thing the spec worried about** — two people analysing one game getting different answers for reasons neither can see — without a `start_sets` table whose only content would be a list of entity keys. Task 6 ships it; `TestASeedRouteContributesItsStepsAsSeeds` and `TestASeedRouteFromAnotherGameIsNotFound` are its two tests.

**O4 — can a route step be a relation? Settled: no, deferred, and the schema does not pretend otherwise.** `route_steps` has no nullable `relation_id` reserved "for later". A reserved column that nothing writes is a column every reader has to have an opinion about. The change it would need is named in the migration comment so whoever does it does not rediscover it.

**O5 — an analysis over an arbitrary subset. Settled: `entity_types` and `relation_types` filters only, and "run this over a D2 query's result" is refused rather than half-built.** Views' own O8 reserved its extension point by making the decoder **refuse unknown top-level keys**, so a `source` key can be added later as an additive change to a document that would previously have been refused. This engine's arguments are a flat struct with no such document, and the equivalent reservation is that its inputs are decoded with `DisallowUnknownFields` — Task 3, `TestAnUnknownAnalysisArgumentIsRefusedRatherThanIgnored`.

**O8 — what error a nonsensical analysis *argument* returns. Settled: `invalid_input`, and this sub-project adds no code for it.** The spec offers two candidates and both are wrong, for the same reason: the code already exists. `metamodel.ValidationError` with `Code: metamodel.CodeInvalidInput` is documented as "a row's own arguments — its key, its label, its colour — being malformed. The fix is to change that argument", and an empty seed set with `include_ungated: false` is precisely that, at path `seed_entities`. `query_invalid` is `internal/views`' code for *a query document* and carries a JSON pointer into one; there is no document here. `invalid_argument` would be a third spelling of `invalid_input`. **A code exists to name a recovery**, and this recovery — change that argument — already has one.

So the whole sub-project adds **exactly one** new wire code, `semantics_undeclared`, and Task 3 argues it: its recovery is not "change your argument" but "declare something about your game's relation types", it carries the catalogue a caller needs to do that, and no existing code carries a payload of that shape.

**O9 — the seam with views. Settled by views, and this plan honours it rather than reopening it.** `internal/graph` owns the SQL primitive; policy is not shared. This package's policy — normalised dependency direction, `any`/`all` gating, containment propagation — lives in `internal/analysis/reach.go` and is not pushed down. Task 4 is the one change to `internal/graph` and it is a change to the *primitive*, not to policy: a walk that can hand back the relation ids along a path. `graph`'s package comment says it has one caller as of that commit; **Task 4 updates that sentence in the same commit that adds the second**, which is the single cheapest instance of "carry the rule one step along" in this plan.

**And one thing the spec proposes that this plan refuses: `analysis_timeout` as a wire code.** The spec's §9 lists it. It does not ship. `internal/views` faced exactly this and refused `query_timeout` with an argument this plan adopts unchanged: SQLSTATE `57014` (`query_canceled`) is already in `metamodel`'s `retryableSQLStates` and already maps to `retryable`, whose meaning is "change nothing and resend", and views extended that error's *message* with which bound to lower rather than adding a code. A timed-out analysis answers `retryable` with a message naming the elapsed budget and the four things that narrow the run: `max_depth`, `entity_types`, `relation_types`, and — new here, and the one that actually helps most — `seed_entity_types`, because a reachability walk seeded from every entity in the game is the expensive shape. **Views refused this code four days ago; adding it here would be the recurring defect in its purest form — a rule established correctly and not carried one step along.** Task 7 pins it with `TestATimedOutAnalysisIsRetryableAndSaysWhichBoundToLower`.

Open questions **6** (should reachability read entity fields — no) and **7** (is the trait vocabulary complete — the mutual-exclusion gap) are not blocking and are left open. Task 3's vocabulary table has one job on this point: the `analysis_traits` column's `<@` check makes adding a trait a migration, and the migration comment says what a mutual-exclusion trait would need, so the cost is on the record.

## What in the shipped code makes this harder than the spec assumes

Seven things. Each has a task.

1. **The walk that shipped is right, and its correction history is the specification for how cycles are read.** `internal/graph/walk.go` returns `(id, depth, path, via_relation, from_id, closed)`, one row per **edge traversal**. Three of its properties were corrections, and all three are load-bearing here:
   - it **emits a row past its cap** (`LIMIT MaxRows + 1`) so a caller that reads `MaxRows+1` rows knows it was truncated — exactly-at-cap and truncated-at-cap are otherwise the same answer, and a walk that cannot tell them apart gets reported to a designer as complete;
   - it **returns the cycle-closing hop, once**, with `closed = true`, and does not expand from it. An earlier shape suppressed the row rather than the recursion, so an *n*-cycle came back with *n−1* of its *n* edges and a self-loop with none — which made the one thing this engine exists to find the one thing that walk could not show;
   - it carries `r.id IS DISTINCT FROM w.via_relation`, without which, under `Direction: Any`, every single edge reports itself as a two-cycle and this engine finds a prerequisite cycle everywhere.

   None of that is reimplemented. Task 7 reads `closed` rows and `path`, and Task 4 adds the one thing missing.

2. **`path` carries node ids and not relation ids, so a cycle's edges cannot be named from the closed row alone.** The spec requires every cycle to carry "the relation ids and relation type keys of the edges that close it", and the first thing a designer checks is whether a type should have been declared gating at all — so naming the *type of every edge* is the finding's most useful field. Reconstructing edges in Go from consecutive node pairs is ambiguous exactly where it matters: two gating relation types between the same pair is the mutual-exclusion shape §3 names as the false-positive case. Task 4 widens `graph.Walk` with an opt-in `CarryRelationPath`.

3. **Normalising `prerequisite_of` against `unlocks` looks like it needs a per-type direction in the walk, and does not.** `graph.Walk.Direction` is one value for the whole walk, and half the gating edges have to be followed backwards. The trick that avoids a second emitter: run `Direction: Any` — whose `near`/`far` are a single arm with a scalar `CASE`, deliberately, so no edge is traversed twice from one node — and put the per-type direction in `EdgePredicate`, which is spliced **inside** the recursion's JOIN where both `r` and `w` are in scope:

   ```sql
   ((r.relation_type_id = ANY($f::uuid[]) AND r.source_id = w.id)
     OR (r.relation_type_id = ANY($b::uuid[]) AND r.target_id = w.id)
     OR (r.relation_type_id = ANY($s::uuid[])))
   ```

   Forward types are followed source→target, reversed types target→source, symmetric types either way. Task 5 does this and `TestANormalisedWalkWillNotFollowAGatingEdgeAgainstItsDirection` is what makes it a decision rather than a coincidence.

4. **`relation_types.semantic_role` is validated in Go against an exported slice *and* by a CHECK constraint, and the pairing exists because of a review finding.** `metamodel.SemanticRoles` exists because a value outside the constraint travelled to Postgres, came back as an untyped check-constraint violation and reached an agent as `internal_error` — a server fault, with no path and no list of what would have been accepted, for something the agent typed. `analysis_traits` gets a `<@` CHECK too, and therefore **gets the same Go-side pairing in the same task**, or it repeats that exact finding. Task 2, `TestATraitOutsideTheVocabularyIsInvalidSchemaAndNotInternalError`.

5. **`relations` will carry six indexes.** It already has `relations_edge_key` (UNIQUE on `relation_type_id, source_id, target_id`), `relations_project_idx (project_id, created_at)`, `relations_source_idx`, `relations_target_idx` and 0008's `relations_type_target_idx`. The spec asks for a sixth, `(project_id, relation_type_id)` — and its stated justification was **false** and says so: `relations_project_idx` does lead with `project_id`. Task 1 does not add it on faith. It runs `EXPLAIN` on this engine's own hottest statement first, as the metamodel plan's correction 6 demanded before adding an index, and adds it only if the plan is a sequential scan — recording the measurement either way, because `relations` is the table that holds a real game's whole graph and every index is write cost on every seeded edge.

6. **`projects.design_version` is a change to a Core table with a new obligation on more than twenty write paths.** The spec asks for a Go-side bump in the same transaction as every write to `entity_types`, `relation_types`, `entities` and `relations` — and names it as "a place a later query can silently forget". That is this project's recurring defect described in advance. Task 1 puts it in statement-level triggers instead and argues it there.

7. **`internal/views` decided the timeout code, the position of page-limit clamping, and the shape of a generated tool description, and this package must not re-decide any of them.** `views.DefaultStatementTimeout`/`HardStatementTimeout` are 5s and 15s and are that package's own constants — this package declares its own two, with its own argument for a different ceiling, and says in a comment that the agreement or disagreement is a conclusion and not an inheritance, exactly as `views/events.go` does for its gating constants.

### Task 1: The schema — traits, the design counter and its triggers, routes

**Files:** creates `internal/db/migrations/0012_analysis.sql`, `internal/db/analysis_schema_test.go`. Modifies nothing.

If another sub-project has taken `0012`, take the next free number; the migration driver is `goose` and ordering is by number, so nothing else moves.

- [x] **Step 1 — `analysis_traits`, as a `text[]` with a closed vocabulary.**

```sql
ALTER TABLE relation_types
    ADD COLUMN analysis_traits text[];

ALTER TABLE relation_types
    ADD CONSTRAINT relation_types_traits_vocab CHECK (
        analysis_traits IS NULL
        OR (cardinality(analysis_traits) > 0
            AND analysis_traits <@ ARRAY['prerequisite_of','unlocks','containment',
                                         'ordering','symmetric','acyclic','annotation']::text[])
    );
```

  `NULL` is **undeclared**; an empty array is refused by the check, so "I have nothing to say about this type" and "this type is deliberately inert" cannot be confused — the second is `{annotation}`. That distinction is the reason `annotation` exists at all and it is why the constraint carries `cardinality(...) > 0` rather than only the `<@`.

  No separate `relation_type_semantics` table: it would be strictly 1:1 with `relation_types`, with no independent lifecycle, no independent permissions and no independent history. Traits arrive on `relation_types.upsert`, are covered by that row's existing `version` and its optimistic-concurrency check, and are deleted when the type is. No `jsonb`: the vocabulary is closed and the database should say so.

  The migration comment states what a **new trait** costs, because §12.7's mutual-exclusion gap will be argued again: a trait is a migration to this constraint, an entry in `analysis.Traits`, a coherence rule, an arm in the resolver, a row in the generated description, and a `semantics_source` case — six places, and the bidirectional tests in Task 3 are what make it six rather than five.

- [x] **Step 2 — `projects.design_version`, bumped by triggers and not by Go.**

```sql
ALTER TABLE projects
    ADD COLUMN design_version bigint NOT NULL DEFAULT 0;

CREATE OR REPLACE FUNCTION bump_design_version() RETURNS trigger AS $$
BEGIN
    UPDATE projects p
       SET design_version = p.design_version + 1
     WHERE p.id IN (SELECT project_id FROM changed);
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;
```

  and, for each of `entity_types`, `relation_types`, `entities`, `relations`, three statement-level triggers using transition tables:

```sql
CREATE TRIGGER entities_design_version_ins
    AFTER INSERT ON entities REFERENCING NEW TABLE AS changed
    FOR EACH STATEMENT EXECUTE FUNCTION bump_design_version();
CREATE TRIGGER entities_design_version_upd
    AFTER UPDATE ON entities REFERENCING NEW TABLE AS changed
    FOR EACH STATEMENT EXECUTE FUNCTION bump_design_version();
CREATE TRIGGER entities_design_version_del
    AFTER DELETE ON entities REFERENCING OLD TABLE AS changed
    FOR EACH STATEMENT EXECUTE FUNCTION bump_design_version();
```

  **Why triggers and not the Go bump the spec asks for.** The spec puts the bump "in the same transaction as the write" and names the risk itself: "a place a later query can silently forget." There are more than twenty such write paths today across `internal/metamodel` and the bulk driver, and the defect this repository has produced at least twenty times is *a rule established correctly and not carried one step along*. A Go bump is that defect with a schedule. A trigger cannot be forgotten by a query written next month, it fires for the bulk driver's `COPY`-shaped writes and for a `DELETE` that cascades, and — the case a Go bump misses entirely — it fires for the cascade when a **type** is removed and takes its entities with it, which is precisely the change most likely to break a stored route verdict.

(b) Every write to a game now updates that game's `projects` row, so concurrent writers to **one game** serialise on it for the remainder of their transactions. That is a real cost and Step 6 measures it rather than reasoning about it. (c) Writes to *different* games touch different rows and do not contend at all.

  Rejected: re-checking every route on every write (seeding a game is hundreds of writes, the cost is quadratic in exactly the situation that matters, and the SSE stream would carry a storm of provisional verdicts). Rejected: comparing `last_checked_at` against `max(entities.updated_at)` — it costs a scan per check and misses deletions entirely, which is the one change most likely to break a route.

### Task 5: `reach.go` — one reachability closure, normalised, gated, containment-aware

**Files:** creates `internal/analysis/reach.go`, `internal/analysis/reach_test.go`.

This is the component views' O8 promised the analysis engine would own, and it is what `routes.check` and `analysis.unreachable` both call. It compiles into `graph.WalkCTE` and emits no recursion of its own.

- [x] **Step 1 — the normalised dependency graph, in the edge predicate.** The engine normalises every gating edge into one internal form, **needed → dependent**, reversing `prerequisite_of` edges as it reads them, so every gating analysis runs over one direction and never thinks about direction again.

  `graph.Walk.Direction` is one value for the whole walk, and half the edges must be followed backwards. The shape that works, with no change to `internal/graph`:

```go
// normalisedWalk builds the one walk every gating analysis runs.
//
// Direction is Any and the per-type direction lives in EdgePredicate.
// That is not a workaround, it is the only shape that is correct here.
// graph.Walk carries one Direction for the whole walk, and a game's
// gating edges point both ways: `requires` reads target-before-source and
// `unlocks` reads source-before-target, and both are gates. Two walks
// unioned would double-count a node reachable through both and would
// need two truncation flags. So: Any, whose near/far are deliberately a
// single arm over a scalar CASE (see graph.WalkCTE's own note on why two
// UNION arms are both illegal in Postgres and wrong when written
// legally), and a predicate that says which types may be followed which
// way. The predicate is spliced INSIDE the recursion's JOIN, where both
// `r` and `w` are in scope, so an edge excluded by direction is an edge
// the walk does not traverse rather than a row it filters afterwards.
func (s *Service) normalisedWalk(name string, sem Semantics, p Params) graph.Walk {
	forward := sem.IDsWithAny("unlocks", "ordering", "containment")
	reverse := sem.IDsWith("prerequisite_of")
	symmetric := sem.IDsWith("symmetric")

	pred := "((r.relation_type_id = ANY($1::uuid[]) AND r.source_id = w.id)" +
		" OR (r.relation_type_id = ANY($2::uuid[]) AND r.target_id = w.id)" +
		" OR (r.relation_type_id = ANY($3::uuid[])))"
	args := []any{forward, reverse, symmetric}
	if p.ExcludeInvalid {
		pred += " AND r.invalid = false"
	}

	return graph.Walk{
		Name:            name,
		ProjectID:       p.ProjectID,
		SeedSQL:         p.SeedSQL,
		SeedArgs:        p.SeedArgs,
		RelationTypeIDs: concat(forward, reverse, symmetric),
		Direction:       graph.Any,
		EdgePredicate:   pred,
		EdgeArgs:        args,
		MinDepth:        0,
		MaxDepth:        p.MaxDepth,
		MaxRows:         MaxWalkRows,
	}
}
```

  `RelationTypeIDs` still carries the union, because `graph.Walk` documents that an **empty list follows no edge at all** — not every edge — and because the type filter is the clause the index serves; the predicate narrows within it.

  `containment` is in `forward` here **and is also walked separately in Task 7**, for two different questions. Reachability propagates from container to contained, which is a forward gate. A containment *loop* is a different report with a different fix, which is Task 7's separate graph. Both statements are true and the comment says both, because a reader who finds `containment` in two places will otherwise assume one of them is a mistake.

- [x] **Step 2 — the invalid-edge decision, written down once.** `Params.ExcludeInvalid` defaults **false**, and the doc comment carries the argument from "Decisions taken since the spec was written" above in full: `invalid` means a row's *fields* stopped fitting, this walk reads only endpoints and relation type, and a verdict about structure must not move when a field schema moves. It also names the contrast — `internal/views/compile.go`'s `invalidFilter` excludes by default, deliberately and for the opposite reason — so a reader comparing the two files finds the disagreement explained rather than assuming one of them forgot.

  The result carries `InvalidEdgesFollowed int`, counted from the walk's own rows. Silence about it would be exactly the "correct and unasserted" defect with the sign flipped: a real limit with no signal.

- [x] **Step 3 — `any` versus `all`.** `any` (the default) is what the walk computes natively: a node is reached the moment one edge reaches it. `all` cannot be a walk, because "every gate of X is reachable" is a property of X's whole in-neighbourhood and not of any one path.

  `all` is computed as a **fixpoint over the reached set**, in Go, from one walk's rows plus one in-degree query: start from the seeds, repeatedly admit an entity all of whose gating in-edges come from already-admitted entities, stop when a pass admits nothing. Bounded by `MaxMaxDepth` passes — a fixpoint that has not converged in 100 passes over a graph whose walk was depth-bounded at 100 has a cycle, and the comment says so and points at `analysis.cycles`. It is a separate code path and its doc comment says it is, rather than pretending the two modes share one.

- [x] **Step 4 — seeds.** `Seeds` resolve to a `SeedSQL` returning one uuid column. Three sources, unioned: `seed_entities` (keys, resolved through `WHERE project_id = $1 AND entity_type_id = $2 AND lower(key) = lower($3)`), `seed_entity_types` (every entity of the type), and `seed_route` (a route's steps, O2's answer).

### Task 7: Analysis 1 — prerequisite cycles

**Files:** creates `internal/analysis/cycles.go`, `internal/analysis/cycles_test.go`.

- [ ] **Step 1 — which walk, and why it needs no widening beyond Task 4.** A cycle report is the existing walk, read for its `closed` rows. `graph.WalkCTE` **returns the cycle-closing hop exactly once**, with `closed = true`, and does not expand from it — a correction made precisely because the earlier shape "made the one thing the analysis engine exists to find the one thing this walk could not show". So:

  - seed: every entity of the considered types (a `SELECT id FROM entities WHERE project_id = $1 AND entity_type_id = ANY($2)`);
  - walk: `normalisedWalk` from Task 5, with `CarryRelationPath: true`;
  - read: rows where `closed`, whose `path` ends with an id it already contains. The cycle is the segment of `path` from the first occurrence of that id to the end; the edges are the corresponding tail of `rel_path`.

  Nothing about the traversal is new. What is new is Step 2.

- [ ] **Step 2 — canonicalisation, which is what makes the report readable.** A four-node cycle is discovered from four starting points and would be reported four times. Each cycle is **rotated so the smallest entity id comes first** and then deduplicated on the rotated id sequence. Self-loops are length-1 cycles and are **reported, not filtered**: they are always a bug and always cheap to fix.

  Rotation is on the id sequence and the **edge sequence rotates with it**, which is the step that gets skipped. `TestACycleAndItsEdgesRotateTogether` asserts that after canonicalisation, edge *i* of the finding joins node *i* to node *i+1 mod n* — read out of the database, not out of the walk's own row, so a rotation that moved the nodes and not the edges is red. **Mutation:** rotate only the node slice; the test goes red on every cycle of length > 1 and stays green on self-loops, which is the discrimination that proves it is testing rotation and not existence.

- [ ] **Step 3 — containment is a separate graph.** Types carrying `containment` are checked in their **own** walk, in their stored direction, and reported as their own finding list, because a containment loop is a different report with a different fix — a hierarchy that is not one, rather than a gate nobody can open. `TestAContainmentLoopIsReportedSeparatelyFromAPrerequisiteLoop` builds one of each and asserts they land in different lists with different type keys.

- [ ] **Step 4 — every finding names the relation type of every edge.** This is the spec's stated reason for Task 4's existence: the first thing a designer checks is whether the type should have been declared gating at all. The clearest real false positive is mutual exclusion — "choosing the Horde locks the Alliance" as two `requires_not` edges — a legitimate two-cycle in a type that reads like a prerequisite, and the fix is a trait declaration, not a code change. `TestAMutuallyExclusivePairIsReportedWithItsRelationTypeSoItCanBeReclassified` builds exactly that fixture and asserts the finding names `requires_not` on both edges.

- [ ] **Step 5 — capped hard, not paginated.** `max_results` default 100, cap 1000, `truncated` when it bites. No cursor: a design with more than a thousand distinct prerequisite cycles has one problem, not a thousand, and paging through them helps nobody. The tool description says this rather than leaving a caller to discover the missing `next_cursor`.

  Findings are ordered **shortest first**. That is not cosmetic: `graph.WalkCTE`'s truncation is `ORDER BY depth`, so a truncated cycle report is a connected prefix of the nearest hops, and reporting the shortest cycles first means a truncated answer is the *most fixable* cycles rather than an arbitrary scatter. `TestATruncatedCycleReportKeepsTheShortestCycles` asserts it with a fixture carrying one 2-cycle and three 8-cycles at `max_results: 1`.

- [ ] **Step 6 — tests:**

  - `TestAnAcyclicGameReportsNoCyclesAndSaysHowManyEdgesItWalked` — the negative half. Empty findings **and** a non-zero `stats.edges_walked`. **Mutation:** filter the walk down to no relation types at all; findings stay empty and `edges_walked` goes to zero, and the test is red. Without that second assertion this test passes on an engine that does nothing.
  - `TestASelfLoopIsReportedAsALengthOneCycle` — including its single edge and its relation type key.
  - `TestATwoCycleIsReportedOnceAndNotTwice` — canonicalisation's core case, discovered from both ends.
  - `TestAFourCycleIsReportedOnceRatherThanFourTimes` — the case the rotation exists for.
  - `TestACycleThatDoesNotPassThroughTheSeedIsFound` — the input that separates a guard computed against the whole path from one computed against the seed alone, which is a property `internal/graph` pins for itself and which this package's seeding could still lose.
  - `TestOrderingTypesAreCheckedForCyclesToo` — `ordering` implies `acyclic`; a `follows` loop is a finding.
  - `TestAnAcyclicOnlyTypeWithNoGatingIsStillChecked` — a `variant_of` declared `{acyclic}` alone, looping. This is the trait's whole reason for existing and it is the one most likely to be quietly dropped from the type set.
  - `TestASymmetricTypeProducesNoCycleFindings` — cycles over a symmetric type are meaningless; a `connects_to` loop is not a finding. Control in the same test: a `requires` loop over the same nodes **is** one, so a walk that found nothing at all cannot pass.
  - `TestCyclesOverAnotherGamesTokenIsScopeViolation`.

- [ ] **Step 7 — the timeout, and the code it does not add.** `TestATimedOutAnalysisIsRetryableAndSaysWhichBoundToLower` sets the package-private statement-timeout knob to something tiny, runs a real walk, and asserts: `errors.Is(err, metamodel.ErrRetryable)`, that the message names the elapsed budget, and that it names `max_depth`, `entity_types`, `relation_types` and `seed_entity_types`. And `TestNoAnalysisTimeoutCodeExists` asserts `Sentinels()` has exactly one member — the bidirectional guard against a later task quietly adding the code this plan argued against.

### Task 8: Analysis 3 — orphans

**Files:** creates `internal/analysis/orphans.go`, `internal/analysis/orphans_test.go`. Modifies `internal/db/queries/analysis.sql`.

The cheapest of the four and **the one with no recursion anywhere in it**. It is an aggregate over `relations`, it is static SQL, and it therefore goes through sqlc like every other statement in this repository — which is worth stating, because three tasks of runtime-built SQL in a row make the fourth look like it should be one too.

- [ ] **Step 1 — the definition.** An entity with no relations at all, counting **every** relation type except those declared `annotation`. ### Task 9: Routes — what a route is, as data

**Files:** creates `internal/analysis/routes.go`, `internal/analysis/events.go`, `internal/analysis/routes_test.go`. Modifies `internal/db/queries/analysis.sql`.

- [ ] **Step 1 — the decision, stated in `routes.go`'s header, because this repository already has a table for saved queries and a second one needs a reason.**

```go
// A route is its own row, and deliberately not a saved view and not a
// kind of one.
//
// The question is fair: `views` is already a table of saved,
// parameterised, versioned artefacts addressed by (project, key), with
// events, an expected_version and a dependency index. A route is saved,
// parameterised, versioned and addressed by (project, key). Four reasons
// it is still its own table, in the order that decided it:
//
//  1. **A view stores a question; a route stores a claim and a verdict
//     about it.** internal/views caches nothing, on purpose: "nothing is
//     cached unless it can say when it went out of date", and its own
//     plan settled (O9) that it adds no design_version because it has no
//     stored result to invalidate. A route is the exception that rule
//     names -- last_check, last_checked_at and
//     last_checked_design_version are a persisted verdict on a named
//     artefact. Putting that on `views` would give that table a cached
//     answer four days after its own sub-project argued it must not have
//     one, and every views query would have to learn a column it never
//     reads.
//
//  2. **A route's payload is authored and ordered; a view's dependency
//     index is derived and unordered.** view_refs is rebuilt from the
//     stored query on every upsert -- it can always be recomputed, which
//     is why a rename is allowed to leave it stale. A route_step cannot
//     be recomputed from anything: it is content somebody wrote, in an
//     order that is the whole point, and its foreign key to `entities`
//     has to survive a deletion as a visible tombstone (ON DELETE SET
//     NULL plus the stored key). No view_refs row has, or could have,
//     that lifecycle.
//
//  3. **A view is defined by things a route has none of.** renderer,
//     renderer_params, layout_mode, layout_seed, background_asset_id,
//     view_positions. Making a route a view means either six columns and
//     a child table that are meaningless for half the rows, or a `kind`
//     discriminator that every existing statement, the list cursor's
//     fingerprint (which keys on the renderer filter) and every renderer
//     requirement check would have to learn. That is a schema change to
//     shipped, tested code in exchange for reusing an `id` column.
//
//  4. **Running a view is a read; checking a route is a write.** views.run
//     is a GET and registerContentRoute leaves it at viewer.
//     routes.check stores its verdict, so it is a POST and takes the
//     editor gate. One table whose rows are read-only under one verb and
//     mutating under another is a permission model with an exception in
//     it.
//
// What the two **do** share is deliberately shared and not duplicated:
// the reachability closure in reach.go (which views' own O8 assigned
// here), internal/paging for the listing cursor, metamodel.RemovedError
// for a version claim against a row that is gone, and the
// (project, key) addressing every row in this product uses.
//
// And one thing a route gives back to the rest of the engine: because a
// route is an ordered list of this game's entities, it is also a **seed
// set** (spec open question 2), which is why analysis.unreachable takes
// `seed_route` and why no start_sets table exists.
```

- [ ] **Step 2 — `UpsertRoute`, addressed by `(project, key)`, replacing the whole step list.** Steps are positional and rewriting them wholesale is simpler for an agent than diffing, and a route is small. The rewrite is `DELETE` then `INSERT` inside the same transaction as the route row's compare-and-set, so a step list never lands beside a route row that rolled back.

  - `expected_version` is **required**: 0 to create a route that must not exist yet, or the version read. Omitting it is `invalid_input`, not a guess.
  - **A non-zero `expected_version` against a route this game does not have is `metamodel.RemovedError`** — `not_found` saying it was removed, not a quiet re-creation. The reason is stronger here than where that error was written: the route that would come back carries a new id, and its stored verdict and every step row hang off that id, so a designer's proved progression and its proof would both be discarded with a success in reply.
  - **At most `MaxRouteSteps` (500) steps, refused and not clamped**, `invalid_input` at `/steps` naming the count and the cap. A route silently truncated to 500 is a proof of a progression that stops halfway and says it holds.
  - Each step resolves `(entity_type_key, entity_key)` to an `entity_id` through a project-filtered lookup. **A key that does not resolve is `not_found` naming the step's position and its key** — not stored as a tombstone. A tombstone is what a *deletion* leaves behind; accepting one on write would let an agent author a route out of typos and be told it holds.
  - `params` holds the reachability parameters the route is checked under (`gate`, `include_ungated`, `propagate_containment`, extra seeds), validated at write time against the same bounds `analysis.unreachable` applies, so a route carries its own definition of what "holds together" means and two people checking it get the same verdict. `TestRouteParamsAreValidatedAtWriteTimeAndNotOnlyAtCheckTime` asserts a bad `gate` is refused by `routes.upsert`, at path `/params/gate`.

- [ ] **Step 3 — the rename lesson, carried one step along.** A step's `entity_type_key` and `entity_key` are **not** rewritten when a type is renamed, exactly as `view_refs.ref_key` is not — `internal/metamodel/rename.go`'s header is the authority. Resolution is by `entity_id`; the stored spelling is what a check reports as moved.

  `TestARenameLeavesARouteStepSpellingTheOldKeyAndTheCheckReportsIt` — rename the entity type, read the route, assert the step still spells the old key, and assert `routes.check` reports `type_renamed` with both spellings. **Mutation:** have `RenameEntityType` tidy `route_steps.entity_type_key`; the test goes red on the second half, and the failure mode it protects against is the one that file already describes — the feature causing the exact failure it exists to prevent.

- [ ] **Step 4 — staleness.** A route whose `last_checked_design_version` is below the project's current `design_version` is **stale**, and stale is its own state: never green, never red. "Not checked against the current design" is a different fact from "broken", and collapsing the two either alarms people wrongly or reassures them wrongly.

  The counter is coarse: any write anywhere in the game marks every route stale, including a typo fix in a description. That is accepted and the doc comment says it is accepted, with the reason — a precise per-route dependency set would have to be maintained on every write and would be wrong the moment a *new* relation makes a previously irrelevant entity relevant. Coarse and correct beats precise and subtly wrong, and re-checking is cheap.

  `last_checked_design_version` is nullable and NULL means **never checked**, which is a third state and not a synonym for stale. `TestANeverCheckedRouteIsNeitherStaleNorHealthy` pins all three states in one test; that is the "an empty answer satisfies any assertion" trap in its route-shaped form.

- [ ] **Step 5 — `GetRoute`, `ListRoutes`, `RemoveRoute`.**
  - `ListRoutes` returns key, name, step count, the three-state check status and `stale`; **no step lists and no stored verdicts** — `routes.get` is where one comes from, mirroring `views.list`'s discipline about not shipping query documents in a listing.
  - Cursor through `internal/paging`, project id first, with the same two tests: `TestARouteCursorFromAnotherGameIsRefused` and `TestTheRouteListingFingerprintIsProjectIdFirstAndCarriesItsDomain`.
  - `RemoveRoute` takes no `expected_version`, and the reason is **the opposite of views'**: `views.remove` argues a view is derived content, cheap to re-upsert from a document the caller holds. A route's steps are authored and its verdict is not reconstructible, so removing one **does** take an `expected_version`. State that inversion in the code, because a reader who has just read `views.remove`'s argument will otherwise assume this is an omission. `TestRemovingARouteRequiresTheVersionAndSaysWhy` asserts the refusal and that the message names what would be lost.

- [ ] **Step 6 — events.** `route.upserted`, `route.removed`, `route.checked`, each with its `minRole` and `humanOnly` **argued in this file's own constants and not aliased from another domain's** — `internal/views/events.go` records exactly this reasoning for its pair, that the three domains happening to agree is a conclusion and not a premise.

  The argument here: `minRole` empty (every member, viewer included) — a route names entities a viewer can already list, and the subscriber who most needs the invalidation is a browser holding a check result that has just gone stale. `humanOnly` false — `routes.check` is mounted on MCP for agents specifically, and an agent looping over check/upsert is the subscriber whose next write is judged against a version another writer just moved.

  `route.checked` carries the route's id, key, version and the **verdict summary** (`ok` / `broken` / counts) and not the per-step list, for the reason `viewEvent` gives: publication order is not commit order, so a payload holding a value a client renders will eventually render the older of two.

  `TestNoRouteEventIsPublishedWhenTheCommitFails` — installs a **deferred** foreign key in its own throwaway database so the commit, and only the commit, fails. A refusal test cannot catch a publish moved inside the transaction, because a rolled-back write and a refused write look identical from outside. This is copied from `internal/metamodel` and `internal/views` because it is the only construction that works.

- [ ] **Step 7 — the isolation tests the spec makes mandatory.** `TestARouteKeyFromAnotherGameIsNotFound`, `TestCheckingARouteWithAnotherGamesTokenIsScopeViolation` (including with an admin's token), `TestARouteStepCannotResolveToAnotherGamesEntity`.

- [ ] **Step 8 — read it back.** `TestARouteReadsBackEverythingItWasWrittenWith` — name, description, `params`, every step with its note and its position, in order. `params` is a free `jsonb` blob written by an upsert, which is **the exact shape `relations.fields` had when it was write-only for a whole sub-project through nine review rounds**, and `note` is the field nobody has a reason to look at. Both are read back here and again over the transport in Task 11.

- [ ] **Step 9 — un-skip Task 5's two seed-route tests** and run `go test ./internal/analysis/...` green.

### Task 10: `routes.check` — the four verdicts

**Files:** creates `internal/analysis/check.go`, `internal/analysis/check_test.go`.

- [ ] **Step 1 — the walk it is.** For each consecutive pair *(n, n+1)*, is step *n+1* reachable given the seed set **plus every step up to n**? That is the reachability closure of Task 5 with the route prefix as seeds — the same walk, called *k* times for a *k*-step route, each call bounded by the same caps.

  **This is the one place the plan spends a walk per step and it is bounded for it:** a 500-step route is 500 walks inside one statement-timeout budget. So `CheckRoute` computes the closure **once**, incrementally: seeds are added, not replaced, and the reached set only grows, so the *k* walks are one walk resumed *k* times over an accumulating seed set. `TestCheckingAFiveHundredStepRouteStaysInsideOneBudget` asserts it completes and records the wall time in a comment — **measuring instead of arguing** is the third thing views ranked among what actually caught defects, and every one of the beliefs it lists was written down and false.

- [ ] **Step 2 — the four verdicts.**

  - `ok`.
  - `missing_entity` — the step's entity was deleted; `entity_id` is NULL and the tombstone key is what the verdict names.
  - `unmet_prerequisite` — the reached set does not include it; names the blocking entities, capped at `MaxBlockers`.
  - `out_of_order` — the step violates an `ordering` relation type that places it after a later step. This is **not** a reachability question and does not use the closure: it is a depth-1 lookup over `ordering`-typed edges between the route's own entity ids, comparing edge direction against step position. Its code comment says it is a different mechanism, because a reader will otherwise assume the closure produced it and look for a bug that is not there.

  Plus `type_renamed`, which is **not a verdict** but a diagnostic carried beside one: a step whose entity resolves by id to a type whose key has moved is still `ok` if it is reachable. Conflating a rename with a break would report a healthy route as broken for a cosmetic change, which is the failure `internal/views`' staleness design exists to avoid and which it solved the same way.

- [ ] **Step 3 — the verdict is stored, and it is the only thing this sub-project caches.** Written back to `routes.last_check` with `last_checked_at` and `last_checked_design_version` read **inside the same transaction as the check**, so a write that lands mid-check cannot make the route look freshly checked against a design it never saw. `TestAWriteDuringACheckLeavesTheRouteStaleRatherThanFreshlyGreen` — starts a check, commits a metamodel write from a second pool, and asserts the stored `last_checked_design_version` is below the project's current value, so the route reads as stale immediately.

  The comment states the pattern this is the single exception to: **nothing is cached unless it can say when it went out of date.**

- [ ] **Step 4 — tests. The negative half is a route that holds.**

  - `TestARouteThatHoldsReportsOkForEveryStepAndNamesItsSeedSet` — five steps, all `ok`, **and** the result names the resolved seed set and the number of steps checked. A check that did nothing returns five `ok`s too if `ok` is the zero value; it is not, and `TestTheZeroVerdictIsNotOk` pins that the verdict type has no meaningful zero — a deliberately invalid zero value, refused if it ever reaches the encoder. This is the "correct and unasserted" discipline applied to an enum, and it is the single cheapest guard in the task.
  - `TestADeletedStepEntityIsMissingEntityAndKeepsItsKey` — delete the entity, check, assert the verdict, the position, and the tombstone key.
  - `TestAStepThatIsNotReachableYetIsUnmetPrerequisiteAndNamesItsBlockers` — with a control that the step **before** it is `ok`, so a check that failed everything cannot pass.
  - `TestAStepThatViolatesAnOrderingRelationIsOutOfOrder` — with a control that the same route with the two steps swapped is entirely `ok`.
  - `TestARouteWhoseTypeWasRenamedIsStillOkAndSaysTheKeyMoved` — the rename diagnostic beside an `ok`.
  - `TestARouteChecksUnderItsOwnStoredParamsAndNotTheCallersDefaults` — writes a route with `gate: "all"`, checks it from a caller that passed nothing, and asserts the stricter verdict. `params` existing and being ignored at check time is the write-only-field defect in its route-shaped form, and this is the test for it.
  - `TestCheckingARouteBumpsNothingAndLeavesTheDesignVersionAlone` — `routes` is not one of the four tables the triggers watch, and it must not be: a check that marked every route in the game stale, including itself, would be a mechanism that invalidates its own output. **Mutation:** add the triggers to `routes`; this test goes red, and it is the only one that would notice.

  Routes: `GET/POST /api/games/{game}/routes`, `GET/DELETE /api/games/{game}/routes/by-key/{key}`, `POST /api/games/{game}/routes/by-key/{key}/check` — mirroring the shipped views route family exactly, including the `by-key` segment.

  `TestEveryContentRouteIsRegisteredAsContent` catches a route added with `mux.HandleFunc`.

- [ ] **Step 6 — SSE.** `route.upserted`, `route.removed`, `route.checked` registered in `internal/web/events.go`'s kind table, each with the phrase that table's bidirectional guard requires (`TestEveryDeclaredKindHasAPhrase` / `TestNoPhraseLacksAKind`).

  **Analyses are not streamed** — they are pull, not push. And **staleness needs no event of its own**: the project's `design_version` rides on the events the UI already receives, and the client compares it locally against each route's `last_checked_design_version`. A `route.stale` event per write would be a storm during seeding and would carry no information the client cannot derive. That means `design_version` has to actually be *on* those events; `TestTheDesignVersionRidesOnEveryMetamodelEvent` is what makes the paragraph above true rather than aspirational, and without it this is a design that only exists in a comment.

- [ ] **Step 7 — drive every tool over the real transport.** `TestEveryAnalysisToolIsCallableOverTheRealTransport`, enumerated **from the registry** so a ninth tool cannot skip it. Views found two defects here that made three tools uncallable by any real client with the entire repository green — an inferred input schema describing a query document as an array of bytes, and an output schema requiring two members the envelope never carried — because every test called the Go functions directly and nothing crossed a schema.

  And, the lesson from that same finding: **call each tool in a state where its answer is non-empty.** Views' transport test ran a view *before* writing a position, and an array of nothing satisfies any item schema at all. So this test seeds a game with a cycle, an unreachable quest, an orphan and a route with one broken step **before** it calls anything.

- [ ] **Step 8 — un-skip Task 6's `TestUnreachableIsReadableOverTheRealTransport`** and the read-back steps Tasks 6 and 9 deferred.
